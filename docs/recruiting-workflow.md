# Recruiting workflow checkpoint — 2026-10-07

Implementation is local and reviewable. No production migration was applied, no email was sent by this work, and no deployment or legal review is claimed.

## New workflow

`POST /api/introductions` requires an authenticated non-anonymous account, central `userHasRecruitingAccess` entitlement (active trial, paid or preserved legacy access), explicit `contactConsent: true`, project/profile UUIDs and an idempotency key. The server checks project ownership and that the profile actually appeared in a stored result. Active profiles with an already shared `free` calendar use that calendar. Other profiles receive one targeted consent email only when a confirmed account address or an approved application with recorded consent exists. Imported research addresses without consent are excluded. No Roman approval is required.

New rows are explicitly `commercial_model = no_fee`. The freelancer receives a recipient-bound HMAC capability valid for seven days. `/api/introductions/consent` GET describes the request without client contact details; POST accepts or declines it. Acceptance conditionally changes only a still-requested row, then exchanges contact details by transaction emails. Profile interest and actual availability remain unconfirmed. A published calendar or contact consent does not assert readiness for the project.

Repeated requests reuse an existing active request and do not resend its email. A database unique index protects concurrent new requests. Historical requests are returned without rewriting their terms. Legacy `/api/search-mandates` GET remains readable; POST returns 410 with an explicit criteria-edit action in the existing workspace instead of creating a new manual/fee-bearing mandate.

## Historical financial boundary

Generated by Supabase CLI 2.120.0: `supabase/migrations/20261007174234_recruiting_no_fee_contacts.sql`.

The additive migration first labels all existing introductions, engagements and search mandates `legacy_placement`, then changes insert defaults to `no_fee`. Existing contract terms, consent audits and invoices are preserved. Commercial-model tags are immutable. New legacy introductions require reference to a historical mandate. Engagements inherit the model from their introduction. A `no_fee` engagement cannot contain a commission, a placement invoice or placement terms. Legacy invoicing and follow-up queries explicitly filter `legacy_placement`. Engagement calculation returns zero commission and waived fee status for `no_fee`; historical calculations still use accepted terms. Existing `PLACEMENT_TERMS` values remain the historical contract snapshot.

The obsolete public placement flag cannot re-enable new fee creation; consent/conversation support is always available. This deliberately changes tests that assumed disabling the flag removed non-calendar profiles.

## Matching boundary

`lib/domain/workflow-instructions.ts` separates operational search/research/contact instructions from candidate requirements before deterministic parsing and AI grounding. Raw project text is preserved. Explicit candidate obligations, actual skill exclusions and hard criteria remain. Matching also ignores contaminated constraint entries from previously saved briefs. It continues to distinguish unknown evidence from contradicted evidence.

## Configuration and rollback

Contact consent uses existing server-only `EMAIL_UNSUBSCRIBE_SECRET` (at least 32 characters) with a separate HMAC purpose. SMTP settings already documented by the existing delivery module (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM`) are required for sending. Secrets are never stored in the documentation. Apply schema before deploying the new backend; if unavailable, new requests fail closed. A code rollback preserves historical data; retain the additive columns and immutable tags, and disable new creation rather than reverting to the old fee workflow for new accounts.
